# Публикация: домены и подключение

Раздел `/publish/domains` (в меню — **Publish → Domains**) — список сайтов, куда система может публиковать. Доступен админам и менеджерам.

## Поддерживаемые типы CMS

- **WordPress** — через стандартный REST API `/wp-json/wp/v2/...`.
- **Custom** — любой сторонний сервис, который принимает HTTP-запрос. Тело запроса собирается из шаблона.

## Создание домена

Кнопка **Добавить домен** сначала спрашивает тип CMS: **Custom CMS** (выбран по умолчанию) или **WordPress**. Дальше пути разные: сайты Custom CMS у нас однотипные и заводятся списком, а у WordPress профили публикации и пароль свои для каждого сайта — там осталась обычная форма.

### Custom CMS — списком

Выберите **Custom CMS** → **Продолжить** и вставьте по одному домену в строке:

```
worldcup2026odds.com - en, es, fr
apuestasmundial2026.net - es, en
```

Формат: `домен - язык1, язык2, …`. **Первый язык — основной.** `https://` писать необязательно.

Endpoint, тело запроса, пути к ID/URL и пароль вводить не нужно — они берутся из общих настроек Custom CMS (раздел **Общие настройки Custom CMS** ниже).

Если общий пароль не задан, добавление не выполнится: появится плашка со ссылкой в настройки. Так сделано намеренно — иначе в системе оказался бы десяток доменов, которые не смогут авторизоваться.

Ошибочная строка не ломает весь список: в конце показывается, сколько **создано / обновлено / пропущено**, и что именно не так с каждой проблемной строкой. Домен, которого ещё нет в DNS, добавить не получится — адрес проверяется на резолвинг, как и при обычном создании.

### WordPress — по одному

Выберите **WordPress** → **Продолжить**, откроется форма. Поля:

- **Name** — подпись для удобства.
- **Base URL** — корневой адрес сайта (например, `https://example.com`).
- **CMS type** — `wordpress` или `custom`.
- **Auth type** — способ авторизации.
- **Languages** — список языков, например `ru, en`. Первый — основной по умолчанию.
- **Multilingual plugin** (только для WP) — `none`, `polylang` или `wpml`. Влияет на то, как передаётся параметр языка при публикации.

### Способы авторизации

- **`wp_app_password`** (только WP) — встроенная функция WordPress «Application Passwords». В админке WP в профиле пользователя сгенерируйте пароль — здесь сохраните логин и этот пароль.
- **`bearer`** — токен в заголовке `Authorization: Bearer ...`.
- **`api_key_header`** — кастомный заголовок (например, `X-API-Key: ...`).

Все секреты шифруются Fernet-ключом и в базе хранятся в зашифрованном виде. В интерфейсе они никогда не показываются повторно — только перезапись.

## Test connection

Каждый домен имеет кнопку **Test connection**. Она:

- проверяет, что Base URL отвечает;
- проверяет, что авторизация валидна;
- для WordPress — пробует достать список типов записей.

Если что-то пошло не так — будет подробная ошибка с кодом ответа и телом.

## Защита от SSRF

Поле **Base URL** не принимает внутренние адреса (`127.0.0.1`, `192.168.x`, `169.254.169.254` и т. п.). Это сделано для защиты от атак, когда злоумышленник пытается заставить наш сервер обращаться к внутренней инфраструктуре.

При запросе на публикацию каждый редирект тоже перепроверяется — если сайт пытается перенаправить на приватный IP, запрос будет прерван.

## Профили публикации (WordPress)

Один домен может иметь несколько **профилей**. Профиль — это «рецепт», как именно публиковать. Полезно, когда на одном сайте есть разные типы записей (`post`, `page`, кастомные post types) или разные шаблоны полей.

Состав профиля:

- **Name** — подпись (например, «Статья», «Кейс», «Лендинг»).
- **Post type** — слаг типа записи в WordPress (`post`, `page`, ...).
- **Fields** — список полей, которые надо отправить. Для каждого поля задаётся:
  - имя (например, `title`, `content`, `excerpt`, `featured_media`);
  - тип (текст, ID медиа, URL медиа, список ID таксономии и т. д.);
  - флаг `is_meta` — если включён, поле уйдёт в массив `meta`, а не в корень объекта.

При публикации система соберёт правильное тело запроса, исходя из выбранного профиля.

### Подсказки post types и таксономий

При редактировании WP-домена поля **post type** и **taxonomy_ids** имеют автодополнение: система сама запрашивает у WordPress список доступных типов и таксономий. Если автодополнение не работает — проверьте права аккаунта в WordPress.

## Custom CMS

Для типа `custom` вместо профилей задаётся:

- **Endpoint path** — путь, который добавляется к Base URL. Запрос идёт методом POST.
- **Body template** — шаблон тела запроса с плейсхолдерами вида `{{title}}`, `{{content}}` и т. д.
- **Response ID path** — точечный путь до ID поста в JSON-ответе (например, `data.id`).
- **Response URL path** — точечный путь до URL поста в JSON-ответе (например, `data.url`).

Имена плейсхолдеров — какие угодно. При публикации они подставятся из формы публикации.

Два имени зарезервированы под язык: **`{{lang}}`** и **`{{language}}`** — в них подставляется язык, выбранный при публикации. Работают оба написания, берите то, которое ждёт Ваш API. Если в форме есть своё поле с таким же именем, приоритет у него.

### Общие настройки Custom CMS

**Настройки → Публикация → Custom CMS** (только админ). Одна конфигурация на все сайты Custom CMS:

- **Endpoint path**, **Body template**, **Response ID / URL path** — то же, что у отдельного домена, но применяется ко всем новым доменам, добавленным списком.
- **Пароль (basic auth)** — один на все сайты Custom CMS, в формате `логин:пароль`. Хранится в зашифрованном виде и после сохранения не показывается.

Значения по умолчанию совпадают с образцом CSV для Custom CMS, так что на свежей установке менять обычно ничего не нужно.

Изменение этих настроек **не трогает уже созданные домены** — они продолжают работать со своей конфигурацией. Чтобы разослать новую конфигурацию по существующим сайтам, есть кнопка **Применить ко всем** (см. ниже).

## Языки и многоязычность

Если у домена больше одного языка, при каждой публикации Вы выбираете язык. Для WordPress с Polylang язык передаётся как `?lang=...` к URL запроса. Для WPML — то же поведение.

### Языки на Custom CMS

Список языков задаётся так же, как у WordPress, — в поле **Languages** домена (первый язык считается основным). А вот **передаётся** язык иначе: у Custom CMS нет ни `?lang=...`, ни плагинов — единственный способ доставить его на сайт — плейсхолдер `{{lang}}` (или `{{language}}`) **внутри body template**.

Поэтому для многоязычного Custom-сайта добавьте язык в шаблон тела запроса, например:

```json
{
  "lang": "{{lang}}",
  "slug": "{{slug}}",
  "title": "{{title}}",
  "content": "{{content}}"
}
```

Если плейсхолдера в шаблоне нет, выбранный язык просто никуда не уйдёт: запрос уйдёт без него, и все языки будут публиковаться на сайт одинаково. Готовый пример на несколько языков есть в образце CSV (**Import CSV → Сайты Custom CMS**).

**Связывание переводов** между языками (один и тот же пост в трёх языках — связан в группу) пока не реализовано. Каждый язык публикуется отдельной записью, без объединения в группу переводов. Это известное ограничение.

## Лимиты на публикацию

Слишком частые запросы к WordPress могут привести к блокировке от хостинга или плагинов безопасности. Поэтому есть **лимиты публикации** — отдельно для каждого домена.

Доступные параметры:

- **Requests per minute (RPM)** — сколько запросов в минуту максимум.
- **Max concurrency** — сколько параллельных публикаций одновременно.
- **Inter-request delay (ms)** — пауза между запросами.
- **Retry max attempts** — сколько раз повторять при ошибках 429/5xx.
- **Backoff base / jitter (ms)** — задержка перед повтором.
- **Respect Retry-After** — учитывать ли заголовок `Retry-After` в ответе 429.

Если поле пустое — значение наследуется из глобальных дефолтов системы. Глобальные дефолты редактирует админ через `PUT /publish/defaults` (UI: Edit Domain → отдельная подсказка).

## Кэш медиа

При публикации с полем **media_url** (URL картинки) система:

1. Скачивает картинку (с лимитом 15 МБ и таймаутом 30 секунд).
2. Загружает её в `/wp-json/wp/v2/media` на стороне WordPress.
3. **Запоминает** соответствие `(domain, source_url) → media_id` в кэше.

Если та же картинка нужна для нескольких строк bulk-таблицы — она загрузится в WordPress только один раз. На следующих строках система переиспользует существующий `media_id`.

В окне редактирования домена есть панель **Media-upload cache** с количеством закэшированных картинок и кнопкой **Clear cache** — пригодится, например, если Вы массово удалили медиа в WordPress и хотите начать с чистого листа.

Если скачать картинку не получилось — публикация поста всё равно состоится, без поля `featured_media`, а в `publish_jobs` сохранится предупреждение.

## CSV-импорт доменов

Несколько похожих доменов удобно завести через CSV: кнопка **Import CSV** на странице доменов. Образец CSV скачивается тут же. Тем же файлом можно и **обновлять** уже заведённые домены — см. раздел **Обновление доменов** ниже.

**Колонки CSV:**

- Обязательные (любая CMS): `name, base_url, cms_type, auth_type`.
- Необязательные (любая CMS): `credentials, languages, multilingual_plugin`.
- Только для Custom CMS: `endpoint_path, body_template, response_id_path, response_url_path, test_endpoint_path`.

`languages` — это один код (`en`) или список через запятую в кавычках (`"en, es, fr"`); пробелы можно не убирать. `body_template` — JSON-объект целиком в одной ячейке (в кавычках, внутренние кавычки удваиваются); переносы строк внутри допустимы. Для `cms_type=custom` обязателен `endpoint_path` — иначе строка будет отклонена.

**Ограничение CSV**: через CSV нельзя завести **профили публикации WordPress** (post types + поля) — формат не выражает вложенность. Для этого есть JSON-импорт ниже. Custom-сайты, наоборот, импортируются из CSV полностью готовыми к публикации.

## Обновление доменов

Раньше повторная загрузка уже существующего домена просто пропускалась, и поменять конфигурацию сразу у многих сайтов было нельзя — только руками у каждого. Сейчас есть три способа, в зависимости от того, что именно меняется.

### 1. Список доменов (Custom CMS)

**Добавить домен → Custom CMS**, галочка **Обновлять существующие домены**.

Без галочки существующие домены пропускаются — так повторная вставка того же списка не перезапишет настроенные сайты случайно. С галочкой у домена **перезаписываются языки и вся общая конфигурация** Custom CMS, а домен из корзины возвращается обратно в работу.

Подходит, когда поменялись языки: вставили тот же список с новыми языками — и всё.

### 2. Import CSV (любая CMS)

Галочка **Обновлять существующие домены** в окне импорта. Работает и для WordPress.

Обновление **частичное**: перезаписываются только те колонки, которые есть в файле и заполнены. Остальное остаётся как было, а пустая ячейка ничего не стирает. Конфигурация Custom CMS сливается по ключам.

Например, файл с колонками `name, base_url, cms_type, auth_type, languages` поменяет только языки — endpoint и body template останутся прежними. А файл, где есть ещё и `endpoint_path`, поменяет заодно endpoint, не трогая тело запроса.

Подходит, когда у сайтов **разные** значения: у каждого своя строка со своими полями.

### 3. Применить ко всем (только Custom CMS)

**Настройки → Публикация → Custom CMS → Применить ко всем**.

Разошлёт текущие endpoint, тело запроса и пароль **сразу по всем** доменам Custom CMS. Языки и названия не трогает. Это то, что нужно, когда контракт CMS изменился для всех сайтов сразу — например, добавилось поле в теле запроса или переехал endpoint.

⚠️ Действие перезаписывает конфигурацию **всех** доменов Custom CMS и не отменяется — поэтому спрятано за отдельным подтверждением. Если у какого-то сайта была своя, отличная от общей конфигурация, она будет потеряна.

## JSON-импорт доменов (с профилями)

Кнопка **Import JSON** рядом с **Import CSV**. Открывается окно: вставьте JSON-массив объектов или загрузите `.json`-файл. Каждый элемент — та же структура, что в `POST /domains`: домен с полным вложенным `publish_config` (несколько профилей, у каждого — `post_type` + `fields[]`) и/или `custom_config`. Лимит 500 элементов за вызов.

Краткая структура одного элемента:

```json
{
  "name": "Site A",
  "base_url": "https://site-a.example.com",
  "cms_type": "wordpress",
  "auth_type": "wp_app_password",
  "credentials": "user:application_password",
  "languages": ["en", "ru"],
  "multilingual_plugin": "polylang",
  "publish_config": {
    "profiles": [
      {
        "name": "Article",
        "post_type": "posts",
        "fields": [
          { "key": "title",   "label": "Title",   "type": "text",     "required": true },
          { "key": "content", "label": "Content", "type": "textarea", "required": true },
          { "key": "slug",    "label": "Slug",    "type": "text" }
        ]
      },
      {
        "name": "Page",
        "post_type": "pages",
        "fields": [
          { "key": "title",   "label": "Title",   "type": "text",     "required": true },
          { "key": "content", "label": "Content", "type": "textarea", "required": true }
        ]
      }
    ]
  }
}
```

В окне есть кнопки **Скачать пример** и **Загрузить пример в редактор** — берите оттуда отправную точку и правьте под свои сайты. На каждое изменение текста снизу показывается превью разбора: «Похоже на корректный JSON — N доменов готовы к импорту». Кнопка Import активна только когда парсинг успешен.

Поведение при ошибках — такое же, как у CSV: каждая «битая» строка попадает в `errors[]` с понятной причиной (validation, конфликт имени, не-WP с `wp_app_password` и т. п.), остальные обрабатываются дальше. По итогам — сводка `inserted / skipped` + список конкретных ошибок по номерам строк.

Под капотом: `POST /domains/import-json`, та же ответная форма `CsvImportResult` ({inserted, skipped, errors[]}).

## Удаление домена (Корзина)

Удаление домена теперь — **soft-delete**: домен переезжает в Корзину, а не пропадает безвозвратно.

- На `/publish/domains` сверху появляется ссылка **Корзина (N)**, когда там что-то лежит.
- На `/publish/domains/trash` — список удалённых доменов с предпросмотром (имя, base_url, тип CMS, языки, время удаления). Учётные данные, профили публикации, лимиты и media-кэш **сохраняются** до окончательного удаления — можно восстановить «как было».
- Кнопки: **Восстановить**, **Удалить навсегда** в каждой строке + чекбоксы для группового восстановления / удаления + **Очистить корзину**.

Что нужно знать:

- **Защита от удаления во время прогона.** Если по этому домену идёт активный Bulk Publish (queued / running / paused), удалить нельзя — будет 409 с предложением сначала отменить прогон.
- **Имена и base_url уникальны только среди активных доменов.** Пока «Site A» в Корзине, можно создать новый активный домен с тем же именем. Если потом попытаться восстановить старый — будет 409 («Cannot restore: an active domain with the same name already exists»). Переименуйте или удалите конфликтующий, потом восстанавливайте.
- **История публикаций сохраняется** — `publish_jobs` ссылаются на домен по FK, который остаётся живым, пока домен в Корзине. После окончательного удаления `domain_id` в исторических записях становится `NULL`, и они отображаются как «(deleted)».
- **Срок хранения** — настраивается на `/settings` → «Срок хранения корзин» отдельно для bulk-таблиц и для доменов. По умолчанию 50 дней; `0` отключает автоочистку. Проверка идёт раз в сутки в 03:15 UTC.
